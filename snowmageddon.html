Snowmageddon

Gameplay Programmer / Co-Developer

Snowmageddon is an in-development Unity/C# arcade combat game from Tiny Cowboy where you play as an evil Snowman wreaking havoc against the kids who made you. Originally a submission for a game Jam, the positive feedback that the team recieved drove development towards a full release. I joined an existing project halfway through development as a co-developer to help the project ship by it's target release in December. During my time on the project, I have contributed with the project's scripting, Unity implementation, bug fixes, polish, and gameplay system improvements.

I'll walk through three changes I made to Snowmageddon: reworking Super Roll, changing how pickups are collected, and moving the shop closer to the player. For each one, I'll explain the problem I started with and what led me to the solution I chose.

Super Roll Refactor

The changes I made to the player's Super Roll ability are the ones I like making for all of my projects: a player facing improvement that also leaves the a little bit codebase cleaner. The ability already worked, but the team felt that the visual presentation could be improved. The task I was assigned to was to change an awkward charge-up and release process into an immediate release of a bowling ball style snowball.

1. Entry point: Code from the Jam.

The existing Super Roll implementation came from the game jam version of the project,the speed and constraints of development was prioritized over maintainability and code elegance.

The visual style of the Super Roll was also the product of the game jam constraints. During charge-up, the giant snowball grew beside the player while an arrow on the ground indicated the direction of the roll. This setup was functional but visually cluttered and less intuitive for players.

2. Codebase: Refactoring opportunity.

Once I started translating the new bowling-ball direction into code, I saw that Super Roll did not need to remain a controller-managed charge feature. PlayerController was already responsible for a lot: movement, camera, throwing, dash, upgrades, health, menus, respawning, and ability logic. This was a good chance to avoid adding more responsibilities to an already broad class.

If I was building this game from the ground up, I likely would have structured things differently from the start, perhaps making a dedicated component for ability management or one specifically for the Super Roll ability. However, because there was an existing codebase with established patterns, I chose the most conservative approach that still could maximize clarity: keep input, aiming, spawning, and resource cost in PlayerController so the feature stayed recognizable beside the project's other abilities; move rolling, growth, collision, impact, and lifetime into GiantSnowball, where that behavior naturally belongs.

1. The controller was already broad

The same frame loop was coordinating movement, camera-facing behavior, dash, snowstorm, interaction, throwing, reload, menus, and Super Roll.

2. Super Roll affected other abilities

The charge state also gated normal throwing, which made the ability feel less isolated than a spawned snowball behavior needed to be.

3. Temporary object state lived in the player

The player controller held the active snowball reference, charge UI, charge timing, charge amount, coroutine, cost, and unlock flags.

3. Removal: Removing the old charge model

Removing the charge-up was my first step toward giving each class a clear responsibility. The player controller handles aiming and launch, and the snowball controls how it rolls, grows, and handles impact. I value the single responsibility principle because it lets me tune the snowball's behavior directly on the object itself and decouple that behavior from the player's controls.

4. Input lifecycle: Super Roll now follows the shape of the player action.

I kept Super Roll input in PlayerController because it already handles most player input and checks whether abilities can be used. A valid press starts aiming, and releasing during an active aim launches the snowball.

Launch is the handoff. From that point on, GiantSnowball manages its own behavior.

Super Roll input before and after

Before: Polling in Update()

During gameplay, Update() called CheckForSuperRoll() each frame. That method handled press and release in one if/else if chain.

private void CheckForSuperRoll()
{
    if (superRoll.action.IsPressed() && !isCharging
        && GetCurrentSnowballs() >= 10)
    {
        isThrowing = false;
        isCharging = true;

        newGiantSnowball = Instantiate(giantSnowball);
        newGiantSnowball.transform.position = rollPoint.position;

        rollChargeCoroutine = StartCoroutine(SuperRollCharge());
        chargeArrow.gameObject.SetActive(true);
    }
    else if (superRoll.action.WasReleasedThisFrame()
        && newGiantSnowball != null)
    {
        StopCoroutine(rollChargeCoroutine);
        isCharging = false;

        Vector3 rollDir = CalculateThrowDirection(rollPoint.position, true);
        rollDir.y = 0f;
        newGiantSnowball.Roll(rollDir, rollForce, 2f);

        ChangeCurrentSnowballs(-rollCost);
        newGiantSnowball = null;
    }
}
After: Input event callbacks

The controller still validates input. The press callback returns early if the player can't start aiming, and the release callback returns early if no aim is active.

private void OnEnable()
{
    superRoll.action.performed += StartAimingSuperRoll;
    superRoll.action.canceled += StopAimingSuperRoll;
}

private void StartAimingSuperRoll(InputAction.CallbackContext context)
{
    if (isAimingSuperRoll || GetCurrentSnowballs() < rollCost) return;

    isThrowing = false;
    isAimingSuperRoll = true;
    StartCoroutine(AimArrow());
}

private void StopAimingSuperRoll(InputAction.CallbackContext context)
{
    if (!isAimingSuperRoll) return;
    isAimingSuperRoll = false;

    GiantSnowball newGiantSnowball = Instantiate(giantSnowball);
    newGiantSnowball.transform.position = rollPoint.position;

    Vector3 rollDir = CalculateThrowDirection(rollPoint.position, true);
    rollDir.y = 0f;

    newGiantSnowball.Roll(rollDir, rollForce);
    ChangeCurrentSnowballs(-rollCost);
}
5. Revamping Giant Snowball: Taking control of its own behavior

GiantSnowball now initializes its Rigidbody, rolls in the chosen direction, grows over time, handles impact, and destroys itself. Growth is controlled with serialized size values, roll time, and an AnimationCurve, so the feel can be tuned without moving that logic back into the player controller.

Code Lens: object-owned snowball lifecycle

This excerpt shows the other half of the refactor: after launch, the snowball owns its own timed behavior.

[RequireComponent(typeof(Rigidbody))]
public class GiantSnowball : Snowball
{
    [SerializeField] private float minSize = 0.5f;
    [SerializeField] private float maxSize = 3f;
    [SerializeField] private float rollTime = 2f;
    [SerializeField] private AnimationCurve scaleOverRollTime; // 1

    void Awake()
    {
        rb = GetComponent<Rigidbody>();
    }

    public void Roll(Vector3 rollDir, float rollForce)
    {
        rb.linearVelocity = rollDir * rollForce;
        StartCoroutine(ExecuteRoll(rollDir, rollForce)); // 2
    }

    private IEnumerator ExecuteRoll(Vector3 rollDir, float rollForce)
    {
        float elapsedTime = 0f;

        while (elapsedTime < rollTime)
        {
            rb.linearVelocity = rollDir * rollForce;
            elapsedTime += Time.deltaTime;

            float rollRatio = Mathf.Clamp01(elapsedTime / rollTime);
            float newSize = Mathf.Lerp(minSize, maxSize, scaleOverRollTime.Evaluate(rollRatio));
            transform.localScale = Vector3.one * newSize;

            yield return null;
        }

        Instantiate(impact, transform.position, transform.rotation);
        Destroy(gameObject);
    }
}
1. Tuning lives with the object

The growth curve and size range belong to the snowball, so tuning the feel does not push logic back into the controller.

2. The snowball governs its own behavior

After launch, ExecuteRoll() coordinates movement, growth, the impact effect, and cleanup inside GiantSnowball.

6. Learning: When a press counts

I like to look for small things I can improve as I work. One hiccup here was figuring out when to start aiming. My first instinct was to use started, which can fire as soon as the trigger begins to move. performed fires once the input reaches the press threshold, which is when I want to check whether the player can start aiming.

One edge case helped me think through the timing. A player could hold the trigger with too few snowballs, reload while still holding, then release and launch a roll that should never have started. I check the cost when the press registers, and release only launches the snowball if aiming actually started.

7. Future work: Refactoring PlayerController

If I had more time, I'd review PlayerController from top to bottom and apply the same single responsibility principle to the rest of the ability logic, looking at what belongs in the controller and what each ability should own. For this task, that would have been too much reinvention for the schedule. The better choice was to make the feature I touched clearer while keeping the surrounding codebase familiar.

This refactor shows how I can simplify how input is handled and separate it from the behavior it triggers, making the code easier to maintain.

Data-Driven Pickups
1. Starting point: Coins left after a wave

After a wave, coins could still be scattered around the map. They already flew toward the player at close range, but collecting them all meant circling the arena before shopping. My task was to have the player automatically collect the leftover coins when the shop opened.

2. Pickup data: One component, different rewards

Penny, nickel, and health pickups already shared a script, with settings stored on each prefab. I moved those settings into PickupSO ScriptableObjects. Each prefab still uses the same Pickup component and points it to an asset with that pickup's reward and movement settings. I also expanded CoinManager into PickupManager so one manager could track active pickups and apply both kinds of rewards.

3. Shop opening: Choosing how pickups collect

Here, my task was to solve a specific issue: handling the leftover pickups when the shop opens. However, our team hadn't settled on a single solution yet. In these scenarios, I always try to design a system that could handle a variety of potential solutions.

I set up each PickupSO to specify its default collection behavior. Normal keeps the close-range behavior. AlwaysAttract pulls pickups toward the player from wherever they landed, and Instant grants the reward immediately. When the shop opens, the team can override the mode on active pickups by reward type. In the gameplay scene, coins use AlwaysAttract so players can see them fly in as the shop opens.

Choosing a shop-open mode by reward type

PickupManager reads the reward and mode pairs from an Inspector list. In the workshop scene, the same shop opening attracts coins and collects health instantly. A reward type left out of the list keeps its current behavior.

Shop Spawning

The shop originally appeared in one central location, which made the player spend too much time crossing the map after a combat round. The assigned task was to make the shop spawn from one of several preset spots based on the player's location.

There was some discussion around random spawning, but I chose authored transforms because they fit the real production constraint. The map has enough terrain and placement issues that fully random spawning would require heavier validation to avoid awkward or unreachable results. With six controlled locations, a simple nearest-location scan was clearer and more reliable than a cleverer search system.

This was less about algorithmic complexity and more about trustworthy placement. For the scale of the feature, the right answer was the one the team could author, inspect, and tune quickly.
