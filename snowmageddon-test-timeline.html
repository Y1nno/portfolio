This version makes the page feel like a guided build log. Instead of asking the reader to absorb one long explanation, it breaks the work into moments: what I inherited, why the visual redesign came first, what I changed in the first pass, what I learned from the input system, and what I would improve with more time.

Super Roll Process

1. Entry point: The old version fit the timeline it was built for.

The existing Super Roll was playable, and I did not see it as "bad code." It was written quickly for a shorter jam-style development horizon, where the goal was to get a working ability into the game. My job was not to judge that context; it was to understand it and improve the feature without pretending the old version had the same goals as the new pass.

The redesign started from a visual and player-facing problem. The snowball grew beside the player during charge-up, which made the ability feel less like a physical snowball fantasy. A bowling-style roll gave the ability a clearer identity: aim, release, roll, grow, impact.

What I respected

The old implementation was solving a two-week problem: make the ability work and be playable.

What I changed

The visual grammar first, then the code architecture once I saw the opportunity.

2. Codebase fit: The visual change opened a code cleanup path.

Once I started translating the new bowling-ball direction into code, I saw that Super Roll did not need to keep living as a player-controller-managed charge feature. PlayerController was already a large script with movement, camera, throwing, dash, upgrades, health, menus, water respawn, and ability logic. This was a good moment to avoid adding more long-term weight to it.

The point was not to rewrite the whole controller. That would have been too much for the task and disruptive for the other developers. The better rule was: stay consistent with the existing ability style, but move ownership where it was obvious and practical. The player should initiate the ability; the snowball should own snowball behavior.

// The old shape mixed input checks, aiming, object placement, and charge state.
if (superRoll.action.IsPressed() && !isCharging)
{
    isCharging = true;
    newGiantSnowball = Instantiate(giantSnowball);

3. Iteration: The first pass removed the old charge model.

The first implementation pass changed the feature from "hold a growing snowball beside the player" toward "aim, release, and roll." I removed the old player-owned charge/growth function, moved giant snowball growth out of PlayerController, and started making CheckForSuperRoll() lighter with early-return flow instead of the old branching charge sequence.

That first pass was intentionally not the final architecture. It made the feature closer to the new design, but it still left the controller checking Super Roll from the regular update path. At that point, the next improvement became clear: the input shape should become event-bound.

Good first move

Remove the charge/growth function and stop making the controller micromanage snowball size.

Remaining issue

CheckForSuperRoll() was still shaped like something that wanted to be asked about every frame.

4. Runtime cleanup: Super Roll became event-started instead of constantly checked.

The part I am proudest of is pulling the ability out of the update loop. The raw performance impact is small, but the principle matters: code should run when it has a reason to run. Super Roll is a press/release ability, so input callbacks were a cleaner fit than repeatedly asking about it during ordinary gameplay frames.

The controller now reacts when Super Roll input is performed, enters a scoped aiming state, and releases the ability when the input is canceled. The player controller remains the right place to answer "can this player start the ability?" and "which direction are they aiming?" It is not the right place to keep owning the snowball after launch.

Code Lens: from checked-every-frame to event-started

The key change is not more code. It is code that runs at the right moment, with the controller initiating the ability and the spawned snowball owning active behavior.

Before: controller-owned check

Input checks, charge state, object references, release handling, UI state, and cleanup all lived inside the controller's Super Roll check.

private void CheckForSuperRoll()
{
    if (superRoll.action.IsPressed() && !isCharging
        && GetCurrentSnowballs() >= 10)
    {
        isThrowing = false;
        isCharging = true;

        newGiantSnowball = Instantiate(giantSnowball);
        newGiantSnowball.transform.position = rollPoint.position;

        rollChargeCoroutine = StartCoroutine(SuperRollCharge());
        chargeArrow.gameObject.SetActive(true);
    }
    else if (superRoll.action.WasReleasedThisFrame()
        && newGiantSnowball != null)
    {
        StopCoroutine(rollChargeCoroutine);
        isCharging = false;

        Vector3 rollDir = CalculateThrowDirection(rollPoint.position, true);
        rollDir.y = 0f;
        newGiantSnowball.Roll(rollDir, rollForce, 2f);

        ChangeCurrentSnowballs(-rollCost);
        newGiantSnowball = null;
    }
}
After: input events start and resolve

The controller subscribes to the input lifecycle, validates the start, guards invalid release, and hands the active roll to GiantSnowball.

private void OnEnable()
{
    superRoll.action.performed += StartAimingSuperRoll;
    superRoll.action.canceled += StopAimingSuperRoll;
}

private void StartAimingSuperRoll(InputAction.CallbackContext context)
{
    if (isAimingSuperRoll || GetCurrentSnowballs() < rollCost) return;

    isThrowing = false;
    isAimingSuperRoll = true;
    StartCoroutine(AimArrow());
}

private void StopAimingSuperRoll(InputAction.CallbackContext context)
{
    if (!isAimingSuperRoll) return;
    isAimingSuperRoll = false;

    GiantSnowball newGiantSnowball = Instantiate(giantSnowball);
    newGiantSnowball.transform.position = rollPoint.position;

    Vector3 rollDir = CalculateThrowDirection(rollPoint.position, true);
    rollDir.y = 0f;

    newGiantSnowball.Roll(rollDir, rollForce);
    ChangeCurrentSnowballs(-rollCost);
}
5. Ownership: The snowball owns the parts that are naturally snowball behavior.

I did not try to move everything out of PlayerController just because I could. I wanted the code to stay recognizable to the rest of the team and consistent with the project's other abilities. The split I used was practical: the controller owns input, aiming, spawning, and cost; GiantSnowball owns rolling, growth, collision, impact, and lifetime.

That gave the object a clearer lifecycle without over-engineering the feature. The snowball initializes its Rigidbody, maintains its rolling motion while alive, grows from minSize to maxSize over rollTime, uses an AnimationCurve for tunable growth feel, spawns its impact effect, and destroys itself.

Code Lens: object-owned snowball lifecycle

The comparison above shows the controller refactor. This annotated excerpt shows what the snowball owns after launch.

[RequireComponent(typeof(Rigidbody))]
public class GiantSnowball : Snowball
{
    [SerializeField] private float minSize = 0.5f;
    [SerializeField] private float maxSize = 3f;
    [SerializeField] private float rollTime = 2f;
    [SerializeField] private AnimationCurve scaleOverRollTime;

    void Awake()
    {
        rb = GetComponent<Rigidbody>();
    }

    public void Roll(Vector3 rollDir, float rollForce)
    {
        rb.linearVelocity = rollDir * rollForce;
        StartCoroutine(ExecuteRoll(rollDir, rollForce));
    }

    private IEnumerator ExecuteRoll(Vector3 rollDir, float rollForce)
    {
        float elapsedTime = 0f;

        while (elapsedTime < rollTime)
        {
            rb.linearVelocity = rollDir * rollForce;
            elapsedTime += Time.deltaTime;

            float rollRatio = Mathf.Clamp01(elapsedTime / rollTime);
            float newSize = Mathf.Lerp(minSize, maxSize, scaleOverRollTime.Evaluate(rollRatio));
            transform.localScale = Vector3.one * newSize;

            yield return null;
        }

        Instantiate(impact, transform.position, transform.rotation);
        Destroy(gameObject);
    }
}
1. Tuning lives with the object

The growth curve and size range belong to the snowball, so tuning the feel does not push logic back into the controller.

2. Lifecycle setup is explicit

The Rigidbody is fetched in Awake() because the object is instantiated and rolled immediately.

3. The coroutine fits the behavior

The snowball has a short linear life: roll, grow, impact, destroy. The coroutine keeps that sequence together.

Tunable feel

Serialized size, roll time, and animation curve keep feel iteration in the Inspector.

Scoped work

The snowball updates while it exists, then destroys itself at the end of its sequence.

6. Learning: The hardest part was understanding the input callbacks.

The most difficult part was not the snowball motion; it was learning the practical difference between input events like started, performed, and canceled. I initially explored started and canceled, but performed better matched the committed press for this button behavior.

That learning fixed a real edge case: the player could hold the input while under the roll cost, reload enough snowballs while still holding, then release into an ability that should never have started. The final version begins only from a valid performed press and guards StopAimingSuperRoll() so an invalid aim session cannot resolve into a spawned giant snowball.

I also moved Rigidbody setup into Awake() because the player controller instantiates the object and immediately calls Roll(). That avoids depending on whether Start() has run before the object is used.

7. Future work: The refactor improved one feature without pretending to solve the whole controller.

If I had more time, I would do a stronger top-to-bottom pass on PlayerController and reassess whether more ability logic belongs somewhere else. For this task, that would have been too much wheel-reinvention for the schedule. The better choice was to make the touched feature cleaner while keeping the surrounding codebase familiar.

What this shows

I can improve game feel and architecture together while working inside an existing team codebase.

What it does not claim

This is not a full player-controller rewrite; it is a focused refactor with practical scope control.
