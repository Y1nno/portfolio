# Portfolio Mission

The portfolio is an argument about my capabilities supported by project evidence.

It should help recruiters and technical interviewers understand what kind of game programmer I am, what roles I am targeting, what I personally implemented, what problems I can reason through, and why my strongest work is worth discussing.

## What This Portfolio Is

- A deliberate, evidence-based presentation of game programming capability.
- A system for turning project history into credible technical case studies.
- A way to create useful interview conversations.
- A source of feedback about skill gaps and future project priorities.
- A shared workspace where multiple AI instances can contribute without losing provenance.

## What This Portfolio Is Not

- A collection of unrelated project pages.
- A gallery where every project receives equal prominence.
- A place for inflated claims or generic adjectives.
- A substitute for evidence, code, assets, or clear attribution.
- A website-design exercise before the content strategy is strong.

## Operating Principle

Every public-facing claim should eventually trace back to evidence.

Use [[Evidence and Provenance Rules]] as the authoritative source for claim status, attribution, and public-use rules.

If a project was collaborative, the case study must distinguish:

- team size;
- my role;
- my responsibilities;
- systems I owned;
- systems I contributed to;
- systems built by others;
- shared decisions where relevant.

## Pipeline

Research -> Personal Positioning -> Project Extraction -> Project Selection -> Case Study Development -> Cross-Project Editing -> Portfolio Implementation -> Review

Each stage produces durable artifacts that become inputs to later stages.
