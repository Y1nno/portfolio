Demons & Dining, Darling!

Unity Developer

Demons & Dining, Darling! is a cooking and dating-sim prototype built in 72 hours for Indie Game Academy's Level 1 course and jam. I was the sole developer on a mixed-discipline team, implementing the playable systems and integrating teammate-created art, writing, and game design inputs.

The prototype shipped publicly on Itch with browser and Windows builds, and the team tied for 3rd place.

Team perspective

This was a mixed-discipline team jam project. I owned the Unity implementation and integration, while teammates contributed the art, writing, and game design direction/content.

The public postmortem credits me with recommending the team's 4 L retrospective format, which helped us reflect on scope, process, and communication after shipping the prototype.

What I contributed

  • Implemented the Unity gameplay loop for timed customer orders, dish preparation, plating, and serving validation.
  • Built pointer-based interaction with game objects: ingredient pickup, drop, stations, and ticket submission.
  • Created data-driven processing and plating station systems that transform ingredients, track ready/ruined states, and produce completed dishes.
  • Integrated Ink dialogue with speaker presentation, choices, dialogue-state input handling, and level callbacks.
  • Integrated teammate-created art, writing, and game design inputs into the working prototype.

System highlights

Order Loop Customer tickets drive dish preparation, serving validation, and feedback.

The order system connects the prototype's cooking loop: customer orders appear, the player prepares a matching dish, submits it to the ticket, and receives reward or penalty feedback.

Problem
The jam prototype needed a complete playable loop that could be understood quickly.
Built
Timed orders, dish validation, plating cleanup, tutorial signals, and customer feedback.
Proof
ResolveOrder() and EvaluateOrder() connect served dishes to active tickets.
Interview handle
Choosing straightforward jam code that shipped the loop rather than overbuilding architecture.
public void ResolveOrder(GameObject order)
{
    if (order != null && orders.Contains(order))
    {
        RemoveOrder(order);
        List<Ingredient> platedIngredients = platingStation.GetIngredients();
        platingStation.ClearIngredients();
        EvaluateOrder(order, platedIngredients);
    }
}

public void EvaluateOrder(GameObject order, List<Ingredient> platedIngredients)
{
    if (GetComponent<TutorialSignaler>())
    {
        GetComponent<TutorialSignaler>().Signal(LevelSignal.ResolvedFirstOrder);
    }
    if (platedIngredients.Count == 1 && platedIngredients[0].definition == order.GetComponent<Ticket>().order)
    {
        PatienceManager.Instance.IncreasePatience(orderApprovalReward);
    }
    else
    {
        AffectionManager.Instance.DecreaseAffection(orderPenalty);
        AddPrompt(servedWrongPrompt);
    }
}
Pointer Interaction Player clicks translate into pickup, drop, station use, and ticket submission behavior.

The pointer interaction layer gave the player one consistent way to touch the cooking loop, from grabbing ingredients to submitting completed dishes while also respecting dialogue-state input locks.

Problem
Many small interactions needed to feel like one readable control scheme.
Built
Click targeting, ingredient pickup and drop, station interaction, ticket submission, and input disabling during dialogue.
Proof
The interaction layer routes player intent into stations, tickets, and held objects.
Tradeoff
The implementation favors speed and clarity over a reusable long-term interaction framework.
Cooking Stations Processing and plating systems transform ingredients into completed dishes.

Processing and plating stations turn raw ingredients into playable cooking steps. They track transformation timing, ready and ruined states, and the ingredients currently assembled into a dish.

Problem
The cooking loop needed more than instant item matching; it needed visible preparation steps.
Built
Station definitions, ingredient transformation, progress feedback, ready/ruined states, and plating behavior.
Proof
Ingredients move through processing stations and plating before being checked against an order.
Interview handle
Keeping station behavior data-driven enough for jam content without slowing production.
Ink Dialogue Dialogue presentation, choices, and level callbacks are integrated into gameplay state.

Ink dialogue connected the dating-sim layer to the Unity prototype. Dialogue state could present speakers and choices, control input flow, and trigger level callbacks for the tutorial and prototype progression.

Problem
The prototype needed narrative presentation without separating dialogue from playable state.
Built
Speaker presentation, portrait handling, choices, action tags, input mode changes, and callbacks.
Proof
Dialogue can pause interaction, present choices, and signal level events back into Unity.
Tradeoff
Jam integration prioritized shipping a working narrative loop over building editor tooling.

What I learned

  • Short jams reward implementation that connects systems quickly instead of overbuilding isolated architecture.
  • Clear attribution matters on team projects: implementation ownership, design direction, art, and writing should each be described separately.
  • A public prototype can be valuable portfolio evidence when paired with honest scope, visible gameplay, and a specific code proof.
