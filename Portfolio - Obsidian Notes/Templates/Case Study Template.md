# Case Study Template

Default progression:

Context -> Problem -> Constraints -> Approach -> Iteration -> Solution -> Evidence -> Reflection

Use [[Case Study]] in `Projects/Project Template/` as the canonical working draft format.

## Flexibility Rule

Do not force every project into an identical story if that weakens the material. The structure is a default, not a cage.

## Required Case Study Checks

- Every major claim links to evidence.
- Personal ownership is clear.
- Team context is clear.
- Technical decisions are explained, not just named.
- Assets support the strongest claims.
- The case study contains enough depth to invite useful interview questions.
- The case study does not overstate competence.

## Technical Review Opening

For flagship projects, the first technical view should make these discoverable quickly:

- what I implemented;
- what problem was solved;
- what constraints mattered;
- how the system was structured;
- why the chosen approach made sense;
- whether code or another artifact supports the claim;
- what changed through debugging or iteration;
- where deeper evidence lives.
