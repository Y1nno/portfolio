False God

(Role: Gameplay Programmer / Project Manager)

10-second summary

False God is a UI-driven roguelike dungeon crawler with turn-based combat, meta-progression, and encounter-driven decision making. Technically, it focuses on modular game systems built around low-coupling architecture, using observer-driven state updates and data-driven configuration.

Technical deep dive

Architecture

False God is built as a set of independent gameplay modules, each responsible for a single system domain. The goal was to avoid tight coupling between mechanics, while still allowing systems to react to one another cleanly.

Major systems include managers for dungeon progression, encounters, combat, player state, inventory, XP, currencies, rites/religion, and scoring. These systems communicate through a Subject/Observer pattern so that modules can respond to game state changes without hard dependencies.

Diagram placeholder: Dungeon Manager → Encounter Manager → Combat Manager → Rewards/Progression → back to Dungeon Flow

Observer flow example: Combat resolves → XP manager updates → UI listens and refreshes → scoring system recalculates.

Configuration is driven through a mix of ScriptableObjects and Unity editor-configurable values, allowing rapid iteration without rewriting core logic.

Key constraints and trade-offs

  • Low coupling: Systems were designed to be independent so new mechanics could be added without rewriting existing modules.
  • Rapid iteration: Editor-driven configuration and ScriptableObjects allow designers to adjust content without programmer involvement.
  • Testability: The testing scene provides a controlled environment to validate mechanics without relying on full game flow.
  • Production speed: Early work prioritized architecture and structure over polish, to support long-term scalability.

Performance and metrics

No formal profiling pass has been performed yet, but the codebase was structured with performance and maintainability in mind. Systems are modular and avoid unnecessary dependencies, reducing the risk of costly cascading updates as the game scales.

  • Planned profiling tools: Unity Profiler, deep profiling for hot paths, and memory allocation tracking.
  • Future optimization targets: combat resolution loops, UI update frequency, and data-driven loading.

Challenges → solutions

Problem: The project required many interconnected systems (combat, progression, dungeon flow, inventory, scoring), and there was a high risk of creating tightly coupled code that would become difficult to extend.

Why it mattered: Roguelikes grow quickly in scope. If systems are interwoven, even small feature additions can cause regressions, slow iteration, and make onboarding new programmers painful.

Final approach: I designed the project around clear system boundaries, using a Subject/Observer pattern so modules could broadcast state changes without knowing who was listening. This allowed mechanics like XP gain, score tracking, and UI updates to react naturally to events without direct coupling.

Result: The architecture supports parallel development, making it easier for multiple programmers to implement systems simultaneously without stepping on each other.

Next steps: As the demo approaches, I plan to formalize event flow rules, add validation tools for ScriptableObject content, and implement lightweight debugging visualizations for combat and dungeon state.
