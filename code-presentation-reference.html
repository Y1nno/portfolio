Code Presentation Reference

Reusable patterns for portfolio code blocks. This is a reference page, not a main-site destination.

Use these patterns when code needs to prove a design decision. Avoid decorative panels, autoplay motion, and long unguided code dumps.

Use side-by-side comparison and annotated code as separate tools. Side-by-side is for contrast; annotation is for guided reading.

Pattern: Side By Side

Use this when a project needs to show a before/after refactor, responsibility change, or implementation decision.

Best for

Refactors where the old and new shapes are meaningfully different: update-loop polling to input events, concrete classes to data-driven assets, or controller-owned behavior to object-owned lifecycle.

Avoid when

The old version is not available, the code is too long to compare cleanly, or the comparison would distract from a more important gameplay clip or diagram.

Code Lens: name the decision being proven

Start with the claim. The reader should know why the code exists before they enter the code block.

Before: describe the old responsibility

Keep this caption short. It should identify the architectural issue, not roast the old code.

private void OldSystem()
{
    CheckInputEveryFrame();
    HoldTemporaryState();
    ManageSpawnedObject();
}
After: describe the new responsibility

Explain what moved, what stayed, and why the new boundary is easier to reason about.

private void OnEnable()
{
    action.performed += StartBehavior;
    action.canceled += StopBehavior;
}

private void StartBehavior()
{
    if (!CanStart()) return;
    SpawnedObject.Run();
}

Pattern: Annotated Code Lens

Use this when one code excerpt needs guided interpretation. This is best when the reader should understand why specific lines matter.

Best for

Final implementations, lifecycle methods, tricky edge cases, data-driven definitions, and snippets where the important part is not obvious from the code alone.

Avoid when

The before/after contrast is the main story. In that case, use side-by-side first and reserve annotations for a separate follow-up excerpt.

Number markers

Use short inline markers like // 1 when a highlighted line maps directly to a note. If a note explains the whole excerpt, place the marker on the method signature or first controlling line.

Code Lens: name the behavior being explained

Start with the claim. Highlight only the lines that support the claim.

private void StartBehavior()
{
    if (!CanStart()) return; // 1
    PrepareTemporaryState();
    SpawnedObject.Run(); // 2
}
1. Guard the state

Explain what invalid case this prevents.

2. Name the handoff

Explain where responsibility moves after this method.

Markup Templates

These are reusable skeletons. Use one pattern at a time unless a section truly needs both in separate beats.

<div class="code-compare">
  <div class="code-compare-header">
    <h4>Code Lens: [decision being proven]</h4>
    <p>[One sentence explaining why this code matters.]</p>
  </div>

  <div class="code-columns">
    <div class="code-column">
      <h5>Before: [old shape]</h5>
      <p>[Short caption.]</p>
      <pre class="code-proof"><code>[before code]</code></pre>
    </div>

    <div class="code-column">
      <h5>After: [new shape]</h5>
      <p>[Short caption.]</p>
      <pre class="code-proof"><code>[after code]</code></pre>
    </div>
  </div>

</div>
<div class="annotated-code">
  <div class="annotated-code-header">

  </div>

    <div>
      <pre class="code-proof"><code><span class="mark">[important line]</span> <span class="code-note">// 1</span></code></pre>
