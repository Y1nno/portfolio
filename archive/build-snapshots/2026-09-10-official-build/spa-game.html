Untitled Spa Game

Co-Developer

Untitled Spa Game is an in-development Unity/C# first-person spa management sim built by a two-person team. Our goal is to create an experience balanced between calm simulation and light-hearted amusement, where players plan and run a spa while managing time, resources, and the emotions of their guests. I built gameplay and simulation systems that accomplish this goal, spanning from guest AI, resource management, and scheduled events.

System highlights

Guest AI Guests choose activities by scoring activities against current needs.

Guests evaluate advertised activities by comparing their current needs against the predicted future state that an activity would create. The scoring favors urgent deficits, so a depleted need can matter more than a larger bonus to an already healthy stat.

Problem
Scripted guest behavior was predictable once the player understood the pattern.
Built
A needs model, advertisement registration, and scoring path for choosing activities.
Proof
ActionSelector.CalculateScore() compares current fulfillment with predicted fulfillment.
Interview handle
Why urgency weighting can make AI choices explainable without making them fixed.
private float CalculateScore(NeedFufillmentAdvertisement ad)
{
    float score = 0f;

    foreach (AdvertisementValue advertisementValue in ad.AdvertisementValues)
    {
        GuestNeedData guestNeed = guestNeedsController.GuestNeeds[advertisementValue.NeedType];
        float guestNeedValue = guestNeed.CurrentValue;
        float futureFulfillment = Mathf.Clamp(
            guestNeedValue + advertisementValue.CalculateFulfillmentAmount(),
            guestNeed.MinValue,
            guestNeed.MaxValue
        );

        score += Appraise(guestNeedValue) - Appraise(futureFulfillment);
    }

    return score;
}

private float Appraise(float value)
{
    float divisor = value;
    if (divisor <= 0.001f)
    {
        divisor = 0.001f;
    }

    return 1f / (divisor / 10f);
}
Resource Flow Items move through definitions, filters, containers, reservations, recipes, and processors.

Spa resources are represented as runtime items backed by reusable definitions. Containers and processors use filters and recipes, which lets new resources be configured without writing a bespoke class for every item.

Problem
Concrete item scripts would become brittle as more spa content was added.
Built
Item definitions, filters, containers, reservations, recipes, and processors.
Proof
Dirty robe, hamper, laundry, and clean robe data form a working resource lifecycle.
Tradeoff
The system is more abstract, so the authoring data needs clear naming and validation.
Scheduling Planning-phase appointment placement becomes timed runtime guest spawning.

Dragged appointment requests are converted into schedule data, queued as timed events, and executed during the Spa Day phase. The player's planning choices become the actual pacing of the simulation.

Problem
The planning phase needed to create real runtime consequences, not just setup flavor.
Built
Appointment requests, draggable views, placement validation, time ticks, lanes, and guest spawning.
Proof
Scheduled appointments create timed events that spawn guests at their selected start time.
Interview handle
Translating pointer placement into valid schedule data with overlap rules.
Checkout Cleanup Guest departure connects state, item generation, container discovery, and fallback behavior.

Checkout turns guest departure into a resource-management workflow. A robe-wearing guest changes, generates a dirty robe, finds a valid container, stores it when possible, and still exits cleanly if no container is available.

Problem
Guest departure had to preserve resource continuity instead of simply deleting state.
Built
Changing flow, dirty item creation, runtime hamper discovery, container insertion, and fallback behavior.
Proof
The dirty robe path connects guest state, subgoals, item definitions, filters, and containers.
Tradeoff
Runtime discovery made the flow more flexible, but required defensive fallback handling.

Takeaways

This project reinforced that strong gameplay systems are rarely isolated. Guest needs, world advertisements, item containers, appointment timing, checkout behavior, and reports become more compelling when they can pass meaningful state between each other.

The work I am proudest of is the flexible foundation: systems that can support new spa content without requiring a bespoke script for every new item, activity, or guest behavior.
